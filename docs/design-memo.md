# ボーリング柱状図データ活用・3D可視化 検討メモ

## 1. ボーリング柱状図とは

地盤調査(ボーリング)の結果をまとめた縦長の図。主な記載内容：

- 深度(掘削深さ)
- 地層構成(土質・境界)
- 標準貫入試験のN値(地盤の硬さ指標)
- 土質記号・色
- 地下水位
- 試料採取位置

用途：建設時の支持層判断、液状化リスク評価、基礎設計(杭長等)。1調査地点=1本の柱状図。複数地点をつなぐと地質断面図・地盤モデルになる。

## 2. データ入手先

### 2.1 KuniJiban(国土地盤情報検索サイト)

- 運営：国土交通省・土木研究所・港湾空港技術研究所
- URL：http://www.kunijiban.pwri.go.jp/jp/
- 提供データ：ボーリング柱状図(PDF+XML)、土質試験結果一覧表
- データ件数：全国 約7.6万本(2010年時点)
- 提供形式：**XML**(構造化データ、無償・自由利用可)。港湾関係は土性図(PDF)のみの場合あり
- 公式の一括ダウンロード機能：地図上選択で**最大100件まで**
- 直URL(例：`?data=boring&type=xml&id=...`)のID総当たりでの全国一括取得は非推奨
  - IDが全国で連番・欠番なしとは限らない
  - サーバー負荷・利用規約未確認のリスクあり
  - → 地図/地名検索で対象IDを取得してから個別リクエストする2段階方式が現実的

### 2.2 国土交通データプラットフォーム(DPP)【本命】

- URL：https://www.mlit-data.jp/
- 概要：国交省・民間データをAPI連携し、検索・表示・ダウンロードを一元化するデジタルツイン基盤
- 国土地盤情報：約25万件(KuniJibanを含み、自治体データ等も統合、2021年時点)
- **API提供**：2023年のバージョンアップで利用者向けAPIが正式提供。**要アカウント登録**
- **API形式：GraphQL**
- データ形式：
  - 柱状図本体：PDF
  - 構造化データ：XML(KuniJibanと同形式)
  - メタデータ：CSV / GeoJSON(2025年版「データ連携標準仕様 Ver1.1」で定義)
- 利用規約：
  - 原則 **CC BY 4.0**(商用利用・改変・複製可、出典表示必須)
  - ただし**データ提供者(国土地盤情報センター等)が個別に定める利活用ルールが優先**されるため、地盤情報固有の追加制限(レート制限等)は登録後にAPI仕様書で要確認
- 公式MCPサーバーあり：https://github.com/MLIT-DATA-PLATFORM/mlit-dpf-mcp.git
  - GraphQLクエリを直接書かずにLLM経由でデータ取得が可能

### 2.3 全国一括DLの可否まとめ

| 方法 | 可否 | 備考 |
|---|---|---|
| KuniJiban ID総当たりスクレイピング | 非推奨 | ToS不明・サーバー負荷リスク |
| KuniJiban 公式一括DL | ○(小規模) | 最大100件/回 |
| DPP API(GraphQL) | ○(想定利用法) | 要アカウント登録、レート制限は要確認、CC BY 4.0で出典表示必須 |

## 3. 3D可視化の方針

### 3.1 データ形式：MLT(MapLibre Tile)

- MVTの後継として2026年1月正式リリース。MapLibre GL JS(5.12.0〜)・MapLibre Nativeにネイティブ対応
- column-oriented(列指向)構造で最大6倍の圧縮、3D座標(標高)・複雑な属性型に対応
- **ただしMLTはあくまで配信フォーマット**(点・線・ポリゴン+属性)。円柱のような任意3Dメッシュ形状はクライアント側のレンダリングロジックで作る必要がある
- 2026年3月、loaders.gl v4.4で`MLTLoader`/`MLTSource`が追加 → **deck.glからもMLTタイルを直接デコード可能に**

### 3.2 円柱表示の実装方針

**方式A：fill-extrusion / ColumnLayerの積み重ね(推奨・低コスト)**

- 1本のボーリングを深度区間(土質層)ごとに分割し、同じ足元ポリゴン(または円柱の位置)・異なる base/height・層ごとの色を持つfeature/インスタンスとして複数重ねる
- MapLibreなら`fill-extrusion-base`/`fill-extrusion-height`、deck.glなら`ColumnLayer`の`getPosition`(z=標高)+`getElevation`(厚み)で実現
- 標準スタイリング/GPUインスタンシングだけで実装でき、カスタムシェーダー不要

**方式B：CustomLayerInterface + Three.js(自由度重視)**

- 頂点カラーでの多層塗り分け、テクスチャ、ラベル表示など柔軟に対応可能
- `MercatorCoordinate`で経緯度→ローカル座標変換して円柱メッシュを配置

### 3.3 deck.glでの実装イメージ(採用方針)

- レイヤー：`ColumnLayer`
- データ構造：深度区間ごとに1レコード
  ```
  { boreholeId, position: [lng, lat, topZ], elevation: thickness, soilType, color, nValue }
  ```
  → 高さ(層厚)を属性として保持し、GPUインスタンシングで大量描画
- 地形との連携：`@deck.gl/mapbox`の`MapboxOverlay`を**interleavedモード**で使用し、MapLibreの3D地形(DEM)と深度バッファを共有(前後関係を正しく描画するため必須)
- 座標変換：`topZ = 地表標高(queryTerrainElevation等で取得) - 上端からの深度`
- 誇張表示：`elevationScale`で鉛直方向を強調(実深度そのままだと視認性が低いため実務でも一般的)
- データ供給：
  - 広域・大量データ → MLTタイル + `TileLayer` + `MLTLoader`で段階的ロード
  - 特定エリアのみ → GeoJSON/Arrow等を直接`ColumnLayer`に渡すシンプル構成

### 3.4 標高タイル(3D地形)との連携

- 国土地理院の標高タイルは`raster-dem`ソースとして利用可能だが、Mapbox系terrain-rgbとは独自エンコーディングが異なるため`encoding: 'custom'`と変換係数指定、または事前変換が必要
- 地表基準高さは`map.queryTerrainElevation(lngLat)`で取得

### 3.5 参考実装：plateau-mlt-pipeline

https://github.com/shiwaku/plateau-mlt-pipeline

Project PLATEAU の CityGML(建築物)をMLT/PMTilesに変換して表示する実例。ボーリングデータのMLTパイプライン設計にそのまま転用できる構成。

**パイプライン構成**

```
CityGML → NDJSON(Python+lxml) → PMTiles(MVT, tippecanoe) → PMTiles(MLT, mlt CLI)
```

- ボーリング版に置き換えると：KuniJiban/DPPのXML → NDJSON(深度区間ごとに1レコード) → PMTiles(MVT) → PMTiles(MLT) という同じ流れがそのまま使える
- 必要ツール：Python 3.12 + lxml、tippecanoe 2.17+、`mlt` CLI(`cargo install mlt`)

**高さ属性の持たせ方(実装上の重要な知見)**

- 高さをfloat(m)ではなく**整数の`z_cm`(地盤面からの高さ、cm単位)**として持たせている
- 理由：tippecanoeは数値をsint/float/doubleに値ごとに書き分けるが、`mlt convert`がそれを文字列列に変換してしまう問題があるため
- → ボーリングの深度・層厚データも、float精度のまま持たせず**整数cm等に丸めてから属性化**するのが安全
- スタイル側では`fill-extrusion-height`に`["*", ["get", "z_cm"], 0.01]`のような式で単位変換して渡す

**表示側のソース定義**

```json
{
  "type": "vector",
  "encoding": "mlt",
  "url": "pmtiles://https://<host>/boring-data.mlt.pmtiles"
}
```
`encoding: "mlt"`はMapLibre GL JS 5.12以降で対応。PMTilesはRangeリクエスト対応サーバーが必要(`npx serve`等)。

**ボーリング用に設計を変える必要がある点**

このリポジトリはfill-extrusion(単色・単一区間の押し出し)前提の建物用パイプライン。ボーリングは「1棟=1フィーチャ」ではなく**「1ボーリング=深度区間の数だけフィーチャ」**になる点がNDJSON生成スクリプトの設計上の違い(3.2節の積み重ね方式と対応)。

**ライセンス・出典表記の型としても参考になる**

PLATEAUデータ(CC BY 4.0等)由来のタイルをCC BY 4.0で再配布し、出典・変換規則の参照元を明記する構成は、DPP/KuniJibanデータ(CC BY 4.0)をMLT化して公開する場合のテンプレートとして流用できる。

### 3.6 「地面に埋め込む」表現の課題

不透明な地形メッシュは地表より下のオブジェクトを通常隠してしまうため、以下いずれかの工夫が必要：

1. **地上に突き出す表現**(最も一般的・実装コスト低)：深度スケールを反転して上方向に伸ばす
2. **深度テスト無効化(X線表示)**：`parameters: {depthTest: false}`(deck.gl)等で地形越しに透過表示。遮蔽関係はリアルでなくなるが「埋まっている感」は出せる
3. **地形の半透明化**：地表マテリアルの不透明度を下げてうっすら透過させる

実用的には「上端(キャップ)は地上に見せ、下は半透明地形越しに見せる」組み合わせが妥当。

## 4. 地質面(層面)の補間による面的表現

### 4.1 最大の課題：層序対比

- どのボーリングのどの層が同じ地質年代・堆積層かを対応づける必要がある
- 単純な土質名一致では誤対比のリスク(地層の尖滅・断層による食い違いなど)
- 完全自動化は困難。専門家による対比表作成が基本、深度・土質区分・N値類似性による半自動マッチング(クラスタリング等)は補助的に活用可能

### 4.2 処理フロー

1. 層境界データ抽出：各層の(x, y, 層上面標高, 層下面標高)をボーリングごとに整理
2. 面の補間：
   - **TIN(不整三角網)**：シンプルだがボーリング疎だとカクカクした面に
   - **IDW(逆距離加重法)**：近いボーリングほど影響大の格子補間
   - **クリギング**：地質統計学的手法、空間相関を考慮でき信頼性高いが計算コスト高
3. メッシュ化：補間結果を3Dメッシュ(グリッド/不整三角網)に変換
4. 描画：CustomLayerInterface + Three.jsで半透明の色分けメッシュとして重ね、円柱(実測点)と同時表示

### 4.3 信頼性への注意

- ボーリング密度が低いと補間面はほぼ推定にすぎず、断層・褶曲・不整合を反映しない/矛盾する面(層の交差、負厚さ)が生じ得る
- 密度が低いエリアは透明度を上げる等、信頼度を視覚的に示すことを推奨。「参考モデル」であることの明示が一般的

### 4.4 処理場所の分離

- **サーバー/前処理側**：Python(scipy, pykrige, geopandas等)で層序対比後データを補間し、グリッド/メッシュ(GeoJSON、glTF等)として書き出し
- **クライアント側(MapLibre/deck.gl)**：出来上がったメッシュを読み込み表示するのみ(ブラウザでの重い補間計算は避ける)
